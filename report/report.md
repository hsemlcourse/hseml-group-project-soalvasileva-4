## 1. Введение и постановка задачи

- **Цель проекта:** 

Предсказать, будет ли авиапассажир удовлетворён перелётом, по характеристикам поездки, класса обслуживания, задержек и оценок качества сервиса.

Такая задача может быть полезна авиакомпании: модель помогает понять, какие факторы сильнее связаны с удовлетворённостью пассажиров, и заранее находить случаи с высоким риском неудовлетворённости.

- **Формулировка задачи:** 

Решается задача бинарной классификации.

Целевой признак: `satisfaction`.

Классы:

- `satisfied` — пассажир удовлетворён;
- `dissatisfied` — пассажир не удовлетворён.

Положительный класс: `satisfied`.

- **Обоснование метрики качества:** 

Основная метрика — ROC-AUC.

ROC-AUC выбрана как основная метрика, потому что модель возвращает вероятность принадлежности пассажира к классу `satisfied`, а нам важно сравнивать модели по качеству ранжирования объектов. Чем выше ROC-AUC, тем лучше модель в среднем ставит более высокие вероятности удовлетворённым пассажирам.

Дополнительные метрики: Accuracy, Precision, Recall, F1-score. Они используются для интерпретации итоговых бинарных предсказаний, но при выборе модели приоритет отдаётся ROC-AUC.

## 3. Обработка и подготовка данных

Обработка данных выполнена в ноутбуке `notebooks/01_EDA.ipynb`.

- **Полная очистка:**

  - Пропуски: числовые признаки заполнялись медианой, категориальные — самым частым значением. Для финальных выборок статистики считались на train-части.

  - Дубликаты: полные дубликаты были удалены.

  - Выбросы: для признаков задержек использовался clipping по 99-му перцентилю. Порог рассчитывался на train-части.

  - Типы данных: проверка и приведение к корректным типам

- **Работа с фичами:**
  
  Добавлены новые признаки:

  - `total_delay` — суммарная задержка вылета и прилёта;
  - `has_delay` — был ли рейс задержан;
  - `is_long_flight` — длинный ли перелёт;
  - `mean_service_score` — средняя оценка сервиса.

  Эти признаки агрегируют информацию о задержках и качестве обслуживания.

- **Визуализации:** 

  В EDA были построены графики:

  - распределение target;
  - пропуски;
  - boxplot задержек;
  - satisfaction rate по `class`;
  - satisfaction rate по `type_of_travel`;
  - satisfaction rate по `customer_type`;
  - распределение `mean_service_score`;
  - correlation heatmap.

  По графикам видно, что удовлетворённость связана с классом обслуживания, типом поездки и оценками сервиса. Особенно заметно влияние бизнес-класса и сервисных оценок.

- **Сплит данных:**

  Данные разделены на train / validation / test в пропорции 70% / 15% / 15%.

  Использовалась стратификация по target, чтобы сохранить баланс классов.

**Как избегали data leakage:**

  - `satisfaction` не используется как feature;
  - вспомогательная колонка `target` не используется как feature;
  - статистики preprocessing считаются на train-части;
  - validation и test не используются при обучении моделей;
  - преобразования признаков выполняются внутри `sklearn Pipeline`.

  | DummyClassifier | 0.500000 | Нижняя граница качества |

Baseline нужен как точка отсчёта. Более сложные модели должны показывать качество выше dummy-модели и простой логистической регрессии.

## 7. Деплой

Для CP3 был реализован локальный деплой модели в двух вариантах:

- FastAPI API для отправки запросов к модели;
- Streamlit-интерфейс для ручного ввода признаков и получения предсказания.

### Интерфейс

Интерфейс реализован с помощью Streamlit в файле:

```text
app/streamlit_app.py
```

В интерфейсе пользователь может задать параметры пассажира и перелёта:

- тип клиента;
- возраст;
- тип поездки;
- класс обслуживания;
- дистанцию перелёта;
- оценки качества сервиса;
- задержку вылета и прилёта.

После нажатия кнопки приложение выводит:

- вероятность класса `satisfied`;
- итоговый предсказанный класс: `satisfied` или `dissatisfied`.

Скриншоты Streamlit-интерфейса сохранены отдельно, потому что форма содержит много полей и не помещается на один экран:

- `streamlit_form.png` — пример формы для ввода параметров пассажира;
- `streamlit_prediction.png` — результат предсказания после нажатия кнопки.

### API

API реализован с помощью FastAPI в файле:

```text
api/app.py
```

Реализованы два endpoint:

  | Endpoint | Метод | Назначение |
  |---|---|---|
  | `/health` | GET | Проверяет, что сервис работает и модель доступна |
  | `/predict` | POST | Принимает признаки пассажира и возвращает предсказание |

Endpoint `/predict` принимает JSON с признаками пассажира, параметрами поездки, оценками сервиса и задержками. Внутри API выполняется тот же feature engineering, что и при обучении модели: рассчитываются `total_delay`, `has_delay`, `is_long_flight` и `mean_service_score`.

Пример ответа API:

```json
{
  "prediction": 1,
  "prediction_label": "satisfied",
  "satisfied_probability": 0.949490076459031
}
```
